#### U6「获取答案」的原理【v0.4 定稿，回应 Q-Q】

**用户明确的原理**（原话要点，权威）：

> **自动化连续请求已完成的测验**，然后记录返回的正确答案
> （**题干、选项、选项文本、题目类型**）。
> 具体接口等抓包数据。

⇒ 这**不是**从当前页 DOM 里抠文本，而是**走接口批量拉取**。要素拆解：

| 要素 | 说明 |
|---|---|
| 触发方式 | 悬浮窗内**手动点按钮**（符合 N5，不自动启动） |
| 请求模式 | **连续请求** —— 逐个/批量拉取「已完成的测验」 |
| 限流 | 走 `common/core/http` 的串行队列，硬下限 200ms（红线 N2） |
| 记录字段 | ① 题干 ② 选项（标识） ③ 选项文本 ④ **题目类型** |
| 答案来源 | **接口返回的正确答案**（不是用户手动填的） |
| 落盘 | JSON，手动导出/导入（方案 A） |
| 待办 | **具体接口未知 ⇒ 必须抓包**（见 `docs/开发文档.md` 抓包最小集） |

**与旧参考脚本的差异（重要）**：旧脚本是从页面 `.ti-q-c` / `.ti-a-c` 等 DOM 节点读题，
因而**强依赖选项顺序**（答案靠 `charCodeAt() - 'A'.charCodeAt()` 定位）。
本项目改为**走接口拿结构化题目与答案**，理论上能拿到 `题目类型`、
从而解决「多选/判断/填空」的判分差异，也不再受页面渲染顺序影响。

⚠️ **风险仍在**：连续请求已完成的测验 = **高频访问站点接口**（🟠 留痕），
且拿到的答案用于后续自动作答 ⇒ 整条链路仍归 🔴 不可逆级，默认关闭 + 二次确认。

#### U6→U7 的答案工作流

用户原话（历史）：**一个机器账号用于刷出答案，然后把答案提供给其他账号使用**。
⇒ 跨账号传递方式已定为 **方案 A：手动导出/导入 JSON 文件**。

**v0.3 新增（Q-N 结论）**：

- **不做账号共存**。两个 UOOC 账号**不同时在同一浏览器登录**，由用户自行切换登录。
- 因此 **U6 的触发方式是完全手动的**：用户在**已登录刷答案账号**的标签页里，
  点悬浮窗上的「获取答案」按钮 → 脚本收集答案 → 导出 JSON。
- 脚本**不自动跨页扫荡**、不后台轮询 ⇒ 符合红线 N5（不自动启动高风险任务）。

#### U9 的 LLM 配置【确认】

- 全局设置页提供 **API URL 输入框 + API Key 输入框**。
- **仅支持 OpenAI Chat 格式**（`{baseUrl}/chat/completions`）。
- 不限定具体厂商 ⇒ 既能填本地 LM Studio（`http://127.0.0.1:1234/v1`），也能填云端。

## 3. 总体架构【确认】框架 + 适配层

```
┌─────────────────────────────────────────────┐
│  悬浮窗（唯一控制面板）                        │
│  基础标签页：全局设置 / 日志 / 状态            │
│  + 各站点注册的自有标签页（可多个）             │
└─────────────────────────────────────────────┘
              ▲ 注册
┌─────────────┴───────────────┐
│  站点适配层 (sites/*)         │
│  bkxk/  uooc/  …             │
└─────────────┬───────────────┘
              ▼ 依赖
┌─────────────────────────────┐
│  框架核心 (core/*)            │
│  bus / storage / log / http   │
│  settings / llm               │
└─────────────────────────────┘
```

**核心原则【拟定】**：

- 站点适配层**只依赖 core**，站点之间**零耦合**；跨站点数据一律经 core 通用存储。
- 每个站点是一个 `SiteAdapter`，声明：`id` / `name` / `match[]` / `tabs[]` / `init()`。
- 悬浮窗不认识任何站点业务，只认 adapter 注册的接口。
- **页面变体层【v0.3 新增】**：一个 adapter 内部可有多个「页面变体」
  （如 UOOC 的旧版 / 新版）。adapter 在 `init()` 时按 URL 分派到对应变体；
  **变体之间共享该站点的存储、设置与功能开关**，但不共享 DOM 逻辑。
  目的：新版页面从零写时，不污染旧版已跑通的代码。

## 4. 悬浮窗规格【确认】

| 要求 | 内容 |
|---|---|
| 形态 | 悬浮窗，是脚本的**唯一**控制面板；**在所有支持的站点都显示**（v0.4 确认） |
| 结构 | **分标签页模式**：标签栏里**平铺**各类标签页 —— 公共标签页 + 各站点专属标签页 |
| 标签页的职责 | ① 开关功能 ② 执行任务 ③ 查看日志 ④ 查看任务（如 bkxk 的抢课任务） |
| 基础标签页 | ① 全局设置（含 LLM 接口设置）② 日志 ③ 登录态 ④ 状态 |
| 参考实现 | `szu_bkxk` 的 `src/ui.js` |
| 跨站点 | 通用信息跨站点存储 |
| **位置 / 大小 / 折叠状态** | **悬浮窗记忆之，且跨站点一致**【v0.4 确认】 |
| **悬浮球位置** | **与面板位置分离、各自记忆**；球默认停在**标题栏折叠按钮的位置**【v0.8 确认】 |
| **首次显示** | **初次访问任何匹配站点都展开面板**；此后按保存的折叠态【v0.8 变更】 |

**【v0.8 变更：首屏显示规则与悬浮球位置】**

1. **首屏显示**（推翻 v0.4 的「非功能页显示悬浮球」）：
   - 用户原话：「**只要是匹配网站初次都显示悬浮窗，后续都根据保存的展开折叠态进行显示**」。
   - ⇒ 匹配站点（`hosts` 命中）**首次访问一律展开面板**，不再按「是不是功能页」决定；
   - ⇒ 用户手动折叠过之后，`ui:collapsed` 被写入，**后续所有页面（含其它站点）都按它显示**。
   - ⇒ **分派结果里的 `autoExpand` 保留**（站点仍可据此决定是否做页面级注入），
     但**不再用于决定悬浮窗的初始折叠态**。
2. **悬浮球位置**：
   - 用户原话：「悬浮球和悬浮窗的位置不统一，我想要悬浮球出现在**关闭按钮的位置**，这样更合适」。
   - ⇒ 面板位置与球位置**分成两份存储**（`ui:panel-pos` / `ui:ball-pos`）；
   - ⇒ 球**首次**出现时（用户还没单独拖过球）位置 = **面板标题栏折叠按钮处**，
     于是「点折叠 → 球落在原地 → 点球展开 → 面板回到原处」在视觉上是一次收起/展开；
   - ⇒ 用户单独拖动球之后，球位置独立记忆，不再跟随面板。

**【v0.3 更新】**

- 功能开关粒度：**每个功能一个复选框**（Q-O）。

**【v0.4 更新】**

- ~~功能列表改为展示该站点自述文档~~ ⇒ **该功能已移除**（Q-R / Q-S 结论）。
  基础标签页只剩 ③ 项（全局设置 / 日志 / 状态）。
- **【v0.7 实现变更】**第 ③ 个基础标签页由「当前站点登录态」改为「**状态**」。
  原因：登录态探测依赖站点接口形态（Q-M 未决、bkxk 另有 cookie+token 双检测），
  在没有抓包前做不出可靠实现；而「状态」页（脚本版本 / 构建时间 / 分派结果 /
  命中适配器 / 存储后端 / GM 可用 / 请求间隔 / 队列深度）现在就有用，且是排障入口。
  **登录态展示推迟到站点适配器落地时，作为各站点标签页的内容。**
- **标签页平铺**（v0.4 用户澄清）：悬浮窗的标签栏里**直接平铺**公共标签页与各站点专属标签页，
  **没有**「先点站点、再点功能」的中间层。
- **站点可以注册不止一个标签页**【v0.4 确认】。参照 `szu_bkxk` 的原有架构，
  一个站点可能提供**五个**标签页：
  **任务 / 监控 / 自定义 / 设置 / 日志**（bkxk 的实例）。
  ⇒ adapter 的 `tabs[]` 是**数组**，元素数量由站点自行决定，悬浮窗只负责平铺。
- **样式隔离【Q-W 结论：混合方案】**：
  - **悬浮窗本体** ⇒ 用 **Shadow DOM**（隔离最彻底，站点 CSS 进不来也出不去）；
  - **注入站点页面内的元素**（如插进章节列表的小按钮）⇒ 用**前缀命名空间** + `all: initial` 重置
    （这类元素必须受站点样式约束才自然）。
  - 推论：站点模块向悬浮窗注册标签页时，**样式必须与 DOM 一起提交给 shadow root**，
    不能靠全局 CSS 生效 —— 这会影响 `common/ui` 的注册接口设计。

**【v0.5 更新：站点总开关取消】**

- **~~站点总开关~~ ⇒ 已移除**（Q-Z 结论：总开关不需要了）。
  - 原 Q-O 的「每站点一个总开关」**作废**；功能门禁**只保留「每个功能一个复选框」**。
  - 原 **Q-T**（总开关与复选框的联动）与 **Q-X**（总开关重开时是否再确认）
    **因失去对象而一并作废**。
  - 红线 **N1 的落点不变**：🔴 功能仍是「默认关 + 复选框 + 二次确认」，只是不再有上层总开关。
- **非支持页面的表现【Q-AA 结论】**：显示**悬浮球**（折叠形态），
  范围**仅限 `szu.edu.cn` 及其子域名**。

## 9. 请求出口与数据落地

### 9.1 请求出口【v0.10 定稿：统一走页面 fetch，即 Q-AE】

**全项目统一使用页面上下文的 `fetch`**（经 `@grant unsafeWindow` 拿到 `unsafeWindow.fetch`），
**不实现 `GM_xmlhttpRequest` 通道**。这推翻了本节早期「使用 `GM_xmlhttpRequest`」的草案。

**理由**：bkxk 的鉴权是「页面 cookie + 请求头 `token` **缺一不可**」。页面 fetch 发出的
`Origin` / `Referer` / `Cookie` / `Sec-Fetch-*` 与站点自身请求**逐字节一致**，
而 `GM_xmlhttpRequest` 是扩展上下文发出的，这些头都要手动伪造、且随时可能被服务端识破。
`@connect` 白名单也随之不再需要。

**代价（用户已明确接受）**：将来 UOOC 若出现跨域或 CSP 阻挡，需要再改一次出口
（届时可加一条 GM 通道作为**回退**，而不是替换）。

**其他要点**：

- 限流队列（N2）放在 `core/http` 的出口层，所有站点共用。
- **凭证双通道**：① 页面 cookie 自动随 `credentials: 'include'` 携带
  ② 站点自定义头（如 bkxk 的 `token`）由 `bkxk/api.ts` 的 `headers()` 显式附加。
- 我们自己的请求会带上 `__szuSkip: true` 标记，供响应接管（hijack）识别并放行 ——
  **改这个标记名要同步改 hijack**。
- 无 `unsafeWindow` 时（例如纯 Node 测试）回退到 `globalThis.fetch`。

### 9.2 数据落地【确认】

| 数据 | 形态 | 位置 |
|---|---|---|
