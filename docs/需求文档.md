## 3. 总体架构【确认】框架 + 适配层

```
┌─────────────────────────────────────────────┐
│  悬浮窗（唯一控制面板）                        │
│  基础标签页：全局设置 / 日志 / 登录态 / 功能列表 │
│  + 各站点注册的自有标签页（可多个）             │
└─────────────────────────────────────────────┘
              ▲ 注册
┌─────────────┴───────────────┐
│  站点适配层 (sites/*)         │
│  bkxk/  uooc/  …             │
└─────────────┬───────────────┘
              ▼ 依赖
┌─────────────────────────────┐
│  框架核心 (core/*)            │
│  bus / storage / log / http   │
│  settings / llm               │
└─────────────────────────────┘
```

**核心原则【拟定】**：

- 站点适配层**只依赖 core**，站点之间**零耦合**；跨站点数据一律经 core 通用存储。
- 每个站点是一个 `SiteAdapter`，声明：`id` / `name` / `match[]` / `tabs[]` / `init()`。
- 悬浮窗不认识任何站点业务，只认 adapter 注册的接口。
- **页面变体层【v0.3 新增】**：一个 adapter 内部可有多个「页面变体」
  （如 UOOC 的旧版 / 新版）。adapter 在 `init()` 时按 URL 分派到对应变体；
  **变体之间共享该站点的存储、设置与功能开关**，但不共享 DOM 逻辑。
  目的：新版页面从零写时，不污染旧版已跑通的代码。

## 6. 登录态与凭证【确认】

**策略**：直接劫持页面已有登录态，**不做接口登录、不处理验证码**。
每个站点账号系统不同 ⇒ 每个 adapter **自己实现取态逻辑**。

| 站点 | 载体 | 已知信息 |
|---|---|---|
| `bkxk.szu.edu.cn` | 页面 `sessionStorage` | 取学号 / 批次码 / 校区 / 令牌（来自原仓库文档）；**v0.3 用户确认：站点同时检测 cookie 与 token** |
| `www.uooc.net.cn` | **待抓包确认**（Q-M） | UOOC 是第三方平台，登录态形态**用户也不清楚，必须分析请求** |

**✅ 已解决（v0.3 / Q-N）**：**不做账号共存**。
两个 UOOC 账号**不同时登录**，由用户自行切换；U6 改为悬浮窗内**手动点按钮触发**。
详见 §2.1 的「U6→U7 的答案工作流」。

**`core/http` 的设计约束【v0.3 新增】**：因为 bkxk 同时检测 cookie 与 token，
`core/http` 必须支持**两种凭证携带方式**：
① 显式注入 `Cookie` 头（`GM_xmlhttpRequest` 默认不带页面 cookie）；
② 显式注入站点自定义头（如 `token`）。
凭证一律只在内存，遵循红线 N3。

#### 7.1.3 三条实测到的坑

1. **`cdn.jsdelivr.net` 在本机解析到非公网 IP**（DNS 污染 / 被墙）⇒
   README 钦定的
   `// @require https://cdn.jsdelivr.net/npm/bonsai-kit@latest/dist/bonsai-kit.umd.min.js`
   **在本环境装不上**。`unpkg.com` 实测可达。
2. **上游仓库的 `dist/` 是 gitignored 的** ⇒ 克隆 GitHub 仓库**拿不到构建产物**，
   必须自己 `npm run build`（需要 esbuild）。
3. **版本号 bug**：`0.0.12` 包里的 `src/index.js`，其 `export const VERSION` 仍写着 `'0.0.11'`
   ⇒ **不要在运行时拿它的 `VERSION` 做版本判断**。

#### 7.1.4 版本与引入策略【v0.3 定稿，回应 Q-H】

先把它拆成两件**正交**的事，混在一起就答不清：

| 维度 | 本项目的决定 |
|---|---|
| **代码从哪来** | npm 依赖 `bonsai-kit`，版本锁在 `package.json` + `pnpm-lock.yaml` |
| **运行时怎么加载** | 由 esbuild **打进本项目自己的 `.user.js`**，**不 `@require` 远程文件** |

⇒ **结论：不用公共 CDN，也不需要 CDN 加速。** 理由：

- 一旦代码被打进自己的 `.user.js`，产物**就在你自己的脚本里**，
  用户装脚本时已经一并拿到，**没有东西需要 CDN 加速**。
  「CDN 加速」这个前提只在 `@require` 远程文件时才成立。
- 而 `@require` 远程方案在本环境**直接不可行**（坑 1），
  且会引入首次安装的网络依赖与离线不可用。
- 构建链已定为 esbuild（§7.2）⇒ `import 'bonsai-kit/components/xxx'` 天然支持，
  且能 cherry-pick 只打包用到的组件，比整包 34.9 KB 更小。

**「fork 自己维护 + 给上游发 PR」是不是更好的选择？**

- 这两件事**不冲突，也不是二选一**，但它们都**不是引入方式**：
  - **给上游发 PR** = 「贡献」。合了更好，没合也不影响你用（你是从自己的代码构建的）。
  - **fork 自己维护** = 「我要改它的代码」。只有在**确实需要打补丁**时才有价值。
- ⇒ 采用**渐进式**：
  1. 先用 npm 依赖（不改它的代码，零维护成本，也不丢上游更新）；
  2. 一旦真的需要改 → fork → 在 fork 里改 → 发 PR 上游 → 本地暂时指向自己的 fork。
- 这样在「不需要改」的时候，**不会因为提前 fork 而背上长期同步的负担**。

**【未决】Q-H 剩余子问题**：是否现在就愿意接受「fork 上游并长期维护」的额外负担？
**我的推荐是「否」** —— 先 npm 依赖，需要时再 fork。**请用户拍板。**

### 7.2 构建链【确认】方案 B：自写构建脚本（esbuild）

## 9. 请求出口与数据落地

### 9.1 请求出口【确认】

**使用 `GM_xmlhttpRequest`**（而非页面 `fetch`）⇒ 需要 `@grant GM_xmlhttpRequest`。

**拟定影响**：

- `core/http` 基于 `GM_xmlhttpRequest` 封装，天然绕过页面同源限制。
- 限流队列（N2）放在 `core/http` 的出口层，所有站点共用。
- **凭证双通道【v0.3】**：支持 ① 显式 `Cookie` 头 ② 站点自定义头（如 `token`）——
  因为 bkxk 同时检测两者，而 `GM_xmlhttpRequest` 默认不带页面 cookie。
- **需注意**：`GM_xmlhttpRequest` 默认不带页面 cookie，
  而 `szu_bkxk` 的写接口依赖请求头里的 `token`（不是 cookie），
  但 UOOC 的登录态形态**待抓包确认** —— 若 UOOC 依赖 cookie，
  则需显式传 `Cookie` 头。**这是开工前必须验证的点（Q-M）。**
