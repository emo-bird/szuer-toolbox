## B. 错误逻辑 / 缺陷候选（分「已核实」与「待复核」）

> 本仓库 717 项测试与严格 IDE 校验已经把大部分逻辑钉得很死，所以这里的错误逻辑大多是
> **防御性缺口 / 资源卫生 / 口径不一致**，而不是能复现的大 bug。逐条说明。

### B1. `uooc/settings.ts:214-222` `readMs()` 空串→0 的防御缺口（已核实）
- **证据**：`readMs` 用 `Number(raw)` 直接转，`Number('') === 0`，而 `0 >= 0` 为真，
  于是「空串存进存储」会静默变成 0ms 等待/超时。
  - 对比：`common/core/limits.ts:45-54` 的 `clampLimit` **专门**把空串/纯空白按
    「没填」(NaN) 处理并回默认值，注释原话：「否则用户清空输入框再保存，间隔会静默变成 0」。
  - UI 路径上 `coerceInput` 会挡掉空串（`settings.ts:161`），所以现在**只有程序化写存储**才会踩到；
    风险低，但是与本项目自定防御口径不一致的漏点。
- 结论类型：**已核实**（代码路径可走通，严重度低）。
- 建议：`readMs` 里对 `typeof raw === 'string'` 先 `trim()`，空串直接回 `fallbackMs`；
  或直接复用 `clampLimit('intervalMs' 之类, raw)` 的判空套路。

### B2. `uooc/intercept.ts` 三个 `wait*` 的定时器不清理（已核实，资源卫生）
- **证据**：`waitCatalog`（:193）/ `waitUnitLearn`（:211）/ `waitCommit`（:265）都
  `setTimeout(() => finish(null), timeoutMs)`；即使 `prime*` 早已满足、`finish` 已被调用，
  这个定时器也一直活到超时（只有 `done` 防重复 resolve，没有 clearTimeout）。
- 影响：一次完整接管里每个任务点都可能 `waitUnitLearn`，会在**同一次会话内**堆积
  若干最长 30s 的孤儿定时器。不致命，但属于「放着不管就会越来越多」的卫生问题。
- 结论类型：**已核实**（严重度低）。
- 建议：把定时器句柄存下来，在 `finish()` 里 `clearTimeout`；三个函数统一改成同一个
  「带清理的可等待」小工具（可以先抽一个内部 helper，别到处复制）。

### B3. `src/main.ts:107` 冗余非空断言（已核实，风格）
- **证据**：`res.adapter !== null ? res.adapter.tabs.map((tab) => ({ siteId: res.adapter!.id, ... })) : []`
  —— 三元已经判过非空，`res.adapter!` 是历史遗留的写法（严格模式下没有警告，但读起来啰嗦）。
- 结论类型：**已核实**（风格）。
- 建议：先 `const adapter = res.adapter;` 再分支，把断言消掉。

### B4. 待复核候选（只给线索，不下结论，需要真机/逻辑推演确认）
1. **`takeover.ts` 的 `fatal()` 竞路**：`fatal`（:178）是 async，多处 `void fatal(...)`；
   顶层 `loop().catch`（:140-145）里发现异常时还会再 `void fatal(...)`。弹窗判重靠
   `dedupeClass`（:77），但两个 `fatal` 之间没有互斥——复核会不会出现
   「两次弹窗/两条状态行/先弹的那个被后一个覆盖」。
2. **bkxk 与 uooc 的 realm 处理不对称**：uooc 有 `intercept.ts:418 installUoocInterceptInFrames`
   专门给 iframe 补装嗅探；bkxk 的 `hijack.ts` 只装顶层 realm（`page-realm.ts` 也只处理顶层）。
   bkxk 抢课/课表在顶层页面，所以可能不需要；但两侧机制不对称，将来 bkxk 若出现 iframe 内容要留意。
3. **`uooc/video.ts` 关开关的「延迟生效」**：`apply()` 只在事件/扫描时跑；用户把二倍速/静音
   关掉后，如果播放器不再触发任何事件，已改过的 `rate`/`mute` 不会立刻回退。
   行为可接受（`WeakMap.applied` 只在下一轮事件里回退），但值得写进文档，别当 bug 乱改。
4. **`uooc/index.ts` `watchNavigation` 对「同站点 hash 跳转」不重分派**（main.ts:148-171）：
   同一个适配器内的 hash 路由变化不会重新 `boot()`，也就不会重新跑 `init`。
   现在旧/新课程页靠 **pathname**（整页导航）区分，所以没实害；但若将来把「旧→新」改成
   hash 路由内切换，两页逻辑将不会切换。记录为边界，别踩。
