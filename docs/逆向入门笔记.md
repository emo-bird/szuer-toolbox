# 第1章 从哪下手：把浏览器变成显微镜

## 1.0 先建立一个认知：网页有「两个世界」

新手最容易犯的错，是以为网页只有一种东西可看——**屏幕上的 HTML**。

实际上任何一个现代网页都同时存在三层证据，而且**越往下越可靠**：

| 层 | 是什么 | 长什么样 | 可靠性 |
|---|---|---|---|
| **① 画面层** | 你眼睛看到的样子 | 截图 | 最低。看不出 ID、看不出谁是谁 |
| **② DOM 层** | 浏览器内存里的元素树 | F12 → Elements | 中。能看到标签、类名、属性，但**看不到数据** |
| **③ 数据层** | 框架（Angular/Vue/React）内存里的对象 | F12 → Console 里跑代码去问它 | **最高。字段名、ID、类型一应俱全** |
| ④ 网络层 | 浏览器和服务器之间的请求 | F12 → Network / 抓包 | 最高，但最费劲（要抓包工具） |

**逆向的本质是：尽量往③④走，别停在①②。**

为什么？因为 ① 和 ② 是「渲染的结果」，而 ③ 是「渲染的原因」。
拿到原因，你就不用去猜结果。

举个本项目里的真例子：

- 停在 ② 的话，我要去数 DOM 里有哪些节点、猜哪个是当前项、猜下一个在哪；
- 走到 ③ 之后，我直接读到了一个数组，里面**每一节都自带 `id`、`finish`、`hide`、`type` 字段**，
  连「我现在在树的哪个位置」都写在里面（`hide === false` 的那条链）。
  一下子省掉了整个「猜」的环节。

## 1.1 第一步永远不是看页面，而是**问清楚页面是谁**

本项目一开始就踩过这个坑，值得单独讲。

**现象**：用户打开的旧版课程页，我去读的时候发现页面变成了错误页
（「哎呀！页面错误! 错误原因 一：您还未选择当前课程」），
`<video>` 数量 = 0，整个 body 只有 3088 字节；而几分钟前明明还是 28650 字节的正常页面。

**当时的错误反应**：以为是「我的操作把页面搞坏了」，于是去试各种修复。

**正确的第一反应**：**先确认「我读到的这个页面，是不是用户正在看的那个页面」。**

要问的四个问题：

1. 这个标签页的 **URL** 是什么？（`#/error/2005836044/` —— 它自己跳错了）
2. 这个标签页的 **title** 是什么？（`登录` —— 说明是登录页，压根不是课程页）
3. 它有几个 **frame**？`<video>` 在哪一帧里？
4. 这个标签页**是不是我操作的那个**？（多标签页/多窗口时尤其重要）

**本项目的真实教训**：用户最后只是**自己在页面里点开了一节视频**，页面就恢复正常了。
也就是说——当时正确的做法是**停下来问用户**，而不是自己折腾。

> **规则**：读到的数据和预期不符时，先质疑「我读的对不对、读的是不是同一个东西」，
> 再质疑「目标是不是坏了」。

## 1.2 工具准备

本项目的取证工具是 **ego-browser**（一个能被我直接操控的 Edge）。核心能力：

- 我能列出所有标签页、切到指定标签页
- 我能在页面里执行任意 JavaScript（`page.evaluate`）

## 1.3 第二坑：**别抄 HTML，抄结构**

新手第二个常见的错误：把网页 HTML 整份复制下来，然后对着它写选择器。

**为什么不行：**

1. HTML 太长。一个课程页面动辄 8 万字符，人的眼睛抓不住重点。
2. HTML 是**动态的**。你现在抄的，和用户操作两下之后的，不是同一份。
3. 现代框架会**按需渲染**——DOM 里只有「当前展开的那一层」，
   你以为「整棵树都在 DOM 里」，其实只有一小段。

**本项目实测证据**（这就是「按需渲染」的实锤）：

- 章级：DOM 里有全部 10 个章 ✅
- 节级：DOM 里**只有当前那一个章的 5 个节**，其余 9 个章的节**根本不在 DOM 里**
  （被 `ng-if="stateParams.chapterId == chapterItem.id"` 挡掉了）
- 资源级：DOM 里**只有当前那一节的资源**

如果你照着 DOM 去写「遍历所有节找下一个视频」，你会发现在第 4 章点得动，在第 5 章点不动——
因为你翻遍 DOM 也找不到第 5 章的节。

**正确姿势**：抄的不是 HTML，是**骨架**——每个元素只留三样东西：

1. 标签名
2. 类名（前几个就够了）
3. **所有 `ng-*` / `v-*` / `href` / `id` 属性**

因为框架的「行为」全写在属性里：`ng-click` 是点了干什么、`ng-repeat` 是从哪个数组循环、
`ng-if` 是什么条件下才渲染、`ui-sref` 是跳到哪个状态。

本项目落盘的骨架长这样（真·原文，`local/capture/uooc-domskel-新.txt`）：

```
   ul | class=level_2 ng-scope | ng-if=!chapterItem.hide && stateParams.chapterId == chapterItem.id
     li | ng-repeat=sectionItem in chapterItem.children | class=ng-scope
       div | class=level_2_title | ng-click=toggleChapter(sectionItem) | ui-sref=main.chapter.section({ sectionId: sectionItem.id }) | id=id_1171204376 | href=#/2005836044/1177669809/1171204376
```

**这一行就告诉了你五件事**：
- 节列表来自 `chapterItem.children` 数组
- 只有当「这个章不是 hide 的」且「URL 里的 chapterId == 这个章的 id」时才渲染
- 点它执行 `toggleChapter(sectionItem)`
- 它跳转的 ui-router 状态是 `main.chapter.section`，参数是 `sectionId`
- **它的 `href` 是 `#/2005836044/1177669809/1171204376`** —— 我可以直接拼这个 URL，不必调用任何函数

比读一坨 HTML 有用得多。

> **技巧**：把「压缩 DOM」这件事写成一个脚本，只读输入、只出骨架。
> 本项目里是 `tools/dom_outline.mjs`。
> （但注意：那个脚本是为另一种输入格式写的，对本次探针的输出**失效**了——
> 见 [1.6 复盘](#16-本次实战复盘含三个真实踩坑)。工具不好用就换，别硬凑。）

## 1.4 第三坑（也是最值钱的一招）：**从 DOM 反查框架内存**

这是把 ② 层打通到 ③ 层的关键动作。

**思路一句话**：DOM 是框架渲染出来的，所以**每一个 DOM 元素身上都挂着一根线，
顺着它能摸到框架内部的那个对象**。

AngularJS 的摸法（本项目用的就是这个）：

```js
// 随便找一个 DOM 元素
const el = document.querySelector('.newlearn_left_card_chapter_list > li');
// 问 Angular：「这个元素归哪个 scope 管？」
const scope = angular.element(el).scope();
// 然后你想看什么就看什么
console.log(Object.keys(scope));
```

**结果**：直接拿到了这个页面的**控制器对象**——所有函数和数据都在上面：

```
goSource, toggleChapter, showSourceList, sourceType, chapterList, courseInfo, ...
```

**更进一步**：`ng-repeat="chapterItem in chapterList"` 这种写法告诉我们，
列表里的每一项都在**子 scope** 上，名字叫 `chapterItem`。所以：

```js
angular.element(第一个li).scope().chapterItem   // 树里的第一个章，含 children
angular.element(第一个li).scope().chapterList   // 整个数组（通过原型链继承拿到的）
```

**这一步的价值**：本项目一下子从「猜 DOM」升级成「读数据」，
拿到了 10 章 54 节的完整树、每个节点的 `id` / `finished` / `hide` / `type`，以及**整张资源类型字典**：

```js
sourceType = { "10":"视频", "50":"附件", "60":"文本", "70":"讨论", "80":"测验" }
```

这张表直接定义了后面所有功能：「自动连播只播视频」= 只认 `type == 10`；
「自动答题」= 去找 `type == 80`。**没有它就得靠猜。**

> **通用套路（换框架也适用）**：
> - Vue 2/3：`el.__vue__` / `el.__vueParentComponent`
> - React：元素上的 `__reactFiber$xxx` 属性，顺着 `memoizedProps` / `stateNode` 走
> - AngularJS：`angular.element(el).scope()` / `.isolateScope()`
> - 万用备选：`getEventListeners(el)`（Chrome/Edge 控制台专有）能看到绑了什么处理函数

## 1.5 采样必须落盘，不然你会淹死在输出里

这条是**纪律**，不是建议。

**反面教材（本次实测）**：
我第一次让探针把整个页面的结构打成 JSON 回传，结果在传输过程中**被截断**了——
JSON 字符串中间被砍掉，我只拿到前 2000 个字符，后面的结构全丢了，白跑一趟。

**正面做法**：在取证脚本里**直接把结果写成文件**：

```js
const fs = await import('node:fs');
fs.writeFileSync('C:\\Project\\szuer-toolbox\\local\\capture\\xxx.json', JSON.stringify(data));
console.log('已落盘，共 ' + data.length + ' 项');   // 回传的只是一句话
```

好处：
1. **不会截断**，再大也完整
2. **不污染对话**——回传的只是「已落盘，共 112 行」，而不是 112 行的内容
3. **可复查**——下次要核对，直接翻文件，不用重跑

本项目把所有采样都放在 `local/capture/`（`local/` 不进 git，因为它可能含隐私数据）。

> **配套纪律**：文件写完之后，**不要整份读回来**。
> 先用 `grep` 找关键词定位行号，再只读那一段。
> 一份 2000 行的采样，真正有用的可能就 30 行。

## 1.6 本次实战复盘（含三个真实踩坑）

把上面所有东西串一遍。目标：搞清楚 UOOC 新旧两版课程页的目录结构，
为「自动连播」做准备。

### 动作 1：确认页面身份

列出所有标签页 → 发现两版各一个 → 切过去 → 读 URL / title / frame 数 / `<video>` 数量。

**产出**：两版 URL 形状一致，都是 `#/{cid}/{chapterId}/{sectionId}/{sourceId}/section`。

### 动作 2：DOM 骨架采样（落盘）

分别对两版跑「DOM 骨架」脚本，各落盘一个文件（112 行 / 85 行）。

**产出**：两版 DOM **完全同构**，只是类名换了皮（`ul.rank-2` ↔ `ul.level_2` 等等）。
这条结论直接省掉了一半工作量——**不用写两套逻辑**。

### 动作 3：数据层采样（落盘）

用 1.4 的招数拿 `chapterList`，递归 dump 成一棵可读的树（105 行）。

**产出**：10 章 / 54 节，两版**逐字相同** → 数据源同一个。
以及那张 `sourceType` 字典。

### 动作 4：确认懒加载（发现了拦路虎）

dump 的时候顺手打印了每个节点的 `unitSource` 长度，发现：

```
L2[1171204376] 第1节 中国传统劳动文化（当前节）   unitSource = 1     ← 有数据
L2[1408189092] 第1节 劳动（非当前）                children = 2       ← 有子节点
L2[465358461] 第2节 从古至今的劳动成就（非当前）   ？？？             ← 字段不存在
```

**结论**：资源清单**只在当前节点上才被填充**，其它节点上是 `undefined`（注意：不是空数组，是字段压根不存在）。

这意味着**不能开局就把整条播放队列算出来**——数据不全。这是设计前必须上报的拦路虎。

### ❌ 踩坑 1：正则里的转义写错，整个脚本挂掉

想匹配 URL 里的 `/`，写成了 `/\\/(\\d+)\\//`。问题是这个脚本要经过**两层字符串**：
我写的源码 → 传给浏览器执行。多转义了一层之后，`\\/` 被解析成「转义反斜杠」+「斜杠」，
而那个**斜杠把正则提前闭合了**，整段代码语法错误。

**教训**：任何「代码套代码」（把代码当字符串传给另一个执行器）的场景，
转义层数要数清楚。**能用字符串拼接就别用正则**，能不用转义就不用。

### ❌ 踩坑 2：把大 JSON 直接回传，被截断

见 [1.5](#15-采样必须落盘不然你会淹死在输出里)。**正确做法是落盘。**

### ❌ 踩坑 3：工具不好用，还在硬凑

本项目有个专门的 DOM 压缩工具 `tools/dom_outline.mjs`。
对这次的探针输出，它**一个字都压不出来**（报「可解析的树/层行: 0」）——
因为它是为另一种输入格式写的。

**教训**：工具是为任务服务的。发现它跟当前输入对不上，
第一选择是**直接读文件**（用 grep 定位 + 分段读），
不要把时间花在「调教工具去适配」。

## 1.7 一张自检清单

下次动手前，照这个顺序过一遍：

- [ ] **① 我在看哪个页面？** URL、title、frame 数、是不是用户正在看的那个
- [ ] **② 关键元素在哪一帧里？**（有 iframe 的页面必查，否则你会对着空气操作）

- [ ] **⑥ 采样落盘了吗？** 别让大输出进对话
- [ ] **⑦ 落盘的文件我是不是只 grep + 分段读了？**
- [ ] **⑧ 遇到和预期不符的，我停下来问用户了吗？**（而不是自己绕过去）

# 第2章 把请求截下来：网络层取证

## 2.0 为什么看完第③层还要看第④层

第1章我们学会了从 DOM 反查框架内存（第③层数据层）。那已经很强了 —— 但它有个天花板：

> **数据层只告诉你「页面现在手里有什么」，不告诉你「它是怎么拿到的」。**

具体到两个真实场景：

1. 我要知道「这门课一共多少节」—— 数据层里确实有那棵树，可**这棵树是站点请求回来的**。
   如果我想在别处也要这份数据（另一个页面、或者我自己的脚本里），
   必须知道**它问的是哪个地址、带什么参数**。
2. 我要知道**服务端的权威值** —— `finished` 到底是 0 还是 1、`video_pos` 播到第几秒。
   数据层里的值可能被前端改过、可能只是缓存。**只有网络层是服务器亲口说的。**

所以第④层要解决的问题是：**这个页面正在跟服务器说什么。**

---

## 2.1 三种看请求的方式，什么时候用哪个

| 方式 | 怎么用 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **F12 → Network** | 打开面板手动翻 | 零成本，字段看得全 | **不能自动化**；一刷新/一跳转记录就断；纯手工 | 第一次摸底：「这个页面到底在请求什么」 |
| **抓包工具**（mitmproxy 等） | 装证书 + 切浏览器代理 | **最权威**；`document-start` 之前的请求也抓得到；还能改包 | 要装环境、要切代理、HTTPS 要装证书 | 「我要一份完整、可反复翻查的证据」 |
| **脚本里自己 hook** | 在 `document-start` 改 `fetch` / `XMLHttpRequest` | **数据直接进我的代码**，能边看边用；零额外请求 | 只看得到「装钩子之后」的请求；写错了会**静默失效**（见 2.3） | 「我要把这份数据**用起来**」—— 本项目 U3 连播走的就是这条 |

**三者不是三选一，是递进**：
先用 F12 摸清有哪些请求 → 不确定就拿抓包工具留档 → 确定要用了再写 hook。

> 本项目对这两条路有明确分工：`docs/开发文档.md` §5 是抓包工作流，
> `src/sites/uooc/intercept.ts` 是 hook 那条路。**两者不互相替代。**

## 2.2 最小可运行的 hook（复制就能用）

### 2.2.1 fetch 版

```js
// 在 document-start 时机执行。win 必须是「页面 realm 的 window」（见 2.3）
const win = unsafeWindow;
const origFetch = win.fetch;

win.fetch = function (input, init) {
  const url = typeof input === 'string' ? input : (input && input.url) || '';
  const p = origFetch.apply(this, arguments);
  if (!url.includes('/home/learn/getCatalogList')) return p; // 只盯要的那几个

  return p.then((res) => {
    // ⚠️ 响应体只能读一次。clone() 一份给自己读，原件照还给页面。
    const copy = res.clone();
    copy.text().then((text) => {
      win.__myCapture = { url, text };
    });
    return res; // 原样放行，别改
  });
};
```

三个关键点，一个都不能少：

1. **`res.clone()` 必须在任何人读 body 之前调用**。忘了 clone 直接 `res.text()`，
   页面那边再想读就会抛 `TypeError: body stream already read` —— **你就把页面弄坏了**。
2. **必须 `return res`**，把原始响应还回去。你是旁路看一份，不是接管。
3. **只在原 promise 上挂 `.then`**，不要 `await` 完再 `new Response()` 造一个 ——
   那样响应头、状态码、流式语义都可能变。

### 2.2.2 XHR 版（老站点更常见）

很多老站点（包括 UOOC）用的是 `XMLHttpRequest`，手段不一样：

```js
const proto = win.XMLHttpRequest.prototype;
const origOpen = proto.open;
const origSend = proto.send;
const WANTED = ['/home/learn/getCatalogList', '/home/learn/getUnitLearn'];

proto.open = function (method, url, ...rest) {
  this.__myUrl = String(url); // open 时先记下「这次请求的是谁」
  return origOpen.call(this, method, url, ...rest);
};

proto.send = function (...args) {
  const url = this.__myUrl || '';
  if (WANTED.some((w) => url.includes(w))) {
    this.addEventListener('load', () => {
      // responseType 不是 '' 或 'text' 时，读 responseText 会直接抛错
      const body = (this.responseType === '' || this.responseType === 'text')
        ? this.responseText
        : this.response;
      win.__myCapture = { url, body };
    });
  }
  return origSend.apply(this, args);
};
```

- 为什么拆成 `open` + `send` 两处？因为**地址在 `open` 时才知道，响应在 `send` 之后才有**。
- 为什么不包整个构造函数？因为**只读旁路不需要包**。包构造函数要处理 `instanceof`、
  `prototype`、静态属性一大堆事，风险面大得多。只有要**改写**响应
  （本项目 `src/sites/bkxk/hijack.ts` 那种）才必须包。

## 2.3 ❌ 踩坑 4（本项目最贵的坑）：hook 装在了沙箱上

**现象**：开关打开了、日志也打了、界面上一切正常，**但站点行为一个字节都没变** ——
响应没被改写，请求也没被截到。**而且 Console 里一条报错都没有。**

**为什么难查**：因为「什么都没发生」和「代码压根没执行」在表面上一模一样。你会去怀疑
选择器写错了、接口名变了、时机不对…… 唯独不会怀疑：**代码执行了，但作用在另一个对象上。**

**根因**：油猴脚本只要在 header 里声明了任何 `@grant`，Tampermonkey 就把脚本放进**沙箱**执行。
沙箱里的 `globalThis` **不是**页面的 `window`。你在沙箱的 `globalThis` 上写
`XMLHttpRequest = 我的包装`，页面自己那份**一个字节都没动** —— 站点发请求用的还是原生 XHR。

本项目把这条教训逐字写在 `src/sites/bkxk/page-realm.ts:4-8`：

> 把包装后的 `XMLHttpRequest` 写在沙箱上，页面自己的那份**一个字节都没动** ⇒
> 站点发请求用的还是原生 XHR ⇒ 响应永远不会被改写，而界面上只是「开关打开了但什么也没发生」，
> **没有任何报错**。

**怎么防**：凡是要「碰页面自己的东西」（`XMLHttpRequest` / `fetch` / 站点自己的全局模块），
**一律经过统一的取 realm 函数**，绝不直接写 `globalThis`：

```js
// src/sites/bkxk/page-realm.ts:16
export function pageRealm() {
  if (typeof unsafeWindow !== 'undefined') return unsafeWindow; // 有沙箱 → 页面 realm
  return globalThis;                                           // 档 1 测试 / @grant none
}
```

> 补充：本仓库里两个都要用 —— `pageRealm()` 给「必须影响页面」的代码用；
> `pageOrSelf()`（`src/common/utils/page.ts`）给「挂个句柄方便调试、页面用不到」的代码用。

**一句话记**：**「什么都没发生」时，优先怀疑作用对象错了，而不是逻辑错了。**

## 2.4 「拦截为主，兜底为辅」：别抢在站点前面

截获的诱惑是「零额外请求」，但**截获不可靠** —— 站点可能换接口、可能命中缓存，
也可能**在你装钩子之前就发过了**。所以正确姿势是两条腿：

1. **先等**：给个超时，等站点自己发；
2. **等不到再自己发**：补一发同源 GET，把结果喂进同一个仓库。

本项目 `src/sites/uooc/intercept.ts` 就是这个结构：
`waitCatalog` / `waitUnitLearn`（等）+ `primeCatalog` / `primeUnitLearn`（喂）+
`peekCatalog` / `peekUnitLearn`（先看看有没有现成的）。

### ⚠️ 这里的真坑：超时定太短，兜底就变成了抢跑

U3 连播第一版把「等站点」的超时定成 **3 秒**。实测时序：

| 时刻 | 发生了什么 |
|---|---|
| 脚本装载（`document-start`） | 钩子装好，开始等站点自己发 `getCatalogList` |
| **+3 秒** | 超时，仓库还是空的 ⇒ 我们**补发**了一发 `/home/learn/getCatalogList?cid=…`（约 35KB） |
| **+约 5 秒** | 站点的 Angular 才起来，**它自己那一发**才出去 |

结果：**每次开课都白打一发 35KB**，「拦截为主」实际退化成「补发为主」。

**教训**：站点那发请求往往是在**框架启动之后**才出去的，而框架启动要好几秒。
任何**固定短超时**都必然抢先。改法是**把兜底触发点系在页面生命周期上** ——
本项目改成「等页面 `load` 之后再等 2 秒，站点仍未发才补发」（`FALLBACK_AFTER_LOAD_MS`），
上头再压一个 30 秒硬上限（`CATALOG_HARD_TIMEOUT_MS`）。

**推广**：**兜底逻辑的触发条件不要写「过了多久」，要写「到了哪个确定的状态」。**

## 2.5 ❌ 踩坑 5：`a.click()` 没抛异常，不代表标签页真的开了

**现象**：连播到「附件」类型时，日志打印「打开附件（后台标签页）：xxx.pdf，OK」。
去看标签页列表 —— **一个 PDF 标签页都没有**。

**根因**：用 JS 造一个 `<a target="_blank">` 再 `a.click()`，如果**当前没有用户手势**
（真实点击、按键这类），浏览器的弹窗拦截器会把它**静默**拦下来：
**不抛异常、不报错、也不告诉你**。代码里写的是
`try { a.click(); return true } catch { return false }`，
于是它一路 `return true` 进了日志。

**教训**：**「没抛异常」≠「成功了」。** 尤其当动作的**结果在代码之外**
（新开了标签页、下载了文件、剪贴板里有了东西）时，必须拿到**证据**再报成功。

**正确做法**（本项目最终采用的）：

- 优先用油猴的 `@grant GM_openInTab`（不受弹窗拦截器管，还能拿到句柄）；
- 没有 GM 才退回 `<a>`；
- 返回值改成**三态** `'gm' | 'anchor' | 'failed'` —— `'anchor'` 那档的日志要**如实写**
  「无法确认是否被弹窗拦截」，不许假报成功。

```ts
// src/sites/uooc/autoplay.ts
export type TabOpenResult = 'gm' | 'anchor' | 'failed';
```

## 2.6 拿到响应之后：先证明你没截错

截到东西 ≠ 截对了。三个自检动作，每个只要一行日志：

1. **打请求参数** —— 把 URL 里的关键参数打出来（本项目打的是 `api.cid` / `api.catalogId`），
   对照你预期的那个 id；
2. **打响应规模** —— `data.length` 或节点数。**数量级不对就是截错了**：
   本项目实测目录树 **104 个节点 / 10 章 / 75 个叶子**，看一眼数字就知道对不对；
3. **交叉验证** —— 响应里的 `cid` / `catalog_id` 应该和请求参数**对得上**。

> ⚠️ 请求日志里**不要打完整 URL**。URL 上可能挂着 token、手机号之类的敏感值。
> 本项目 `src/common/core/http.ts` 里有个 `safePath()`，就是「只留 path + hash」用的。

## 2.7 自检清单（网络层版）

- [ ] **① 我看的是哪个请求？** 地址、方法、关键参数、有没有带 token
- [ ] **② 我要「看」还是「改」？** 只看就别包构造函数，风险小得多
- [ ] **③ 钩子装在哪个 realm？** 有 `@grant` 就必须走 `pageRealm()` / `pageOrSelf()`
- [ ] **④ 读响应体之前 clone 了吗？**（fetch）`responseType` 判了吗？（XHR）
- [ ] **⑤ 兜底触发条件是「时间」还是「状态」？** 别用固定短超时
- [ ] **⑥ 我报「成功」时有证据吗？** 还是只是「没抛异常」
- [ ] **⑦ 日志里有没有漏出敏感字段？**
- [ ] **⑧ 截到的数据，我验证过它的规模与参数对得上吗？**
