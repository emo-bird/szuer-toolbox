## 3. 优化 / 简化建议（在清单 B/C 之外）

### 3.1 定时器清理收敛为「只修 `waitCommit`」
删除 catalog/unit 层（§2.1）后，B2 只剩 `waitCommit`(:255-267) 一个：
```ts
// 现在：只防重复 resolve，定时器活到超时
const finish = (v: CommitResult | null): void => { if (done) return; done = true; resolve(v); };
commitWaiters.push(finish);
setTimeout(() => finish(null), timeoutMs);
// 建议：存句柄，finish 里 clearTimeout（primeCommit 走到的 waiter 分支也在同一次会话内清掉）
```

### 3.2 `fatal()` 竞路补一个「已弹过」守卫
`fatal`(:178) 是 async，`loop()` 内多处 `await fatal(...)`，顶层 `loop().catch` 还会再 `void fatal(...)`。
`dedupeClass` 只防了**弹窗遮罩**叠加；**状态行** `statusText` 是 last-writer-wins，两条不同 fatal
会先后覆盖。建议在 `fatal` 开头加一个 `if (fatalShown) return; fatalShown = true;`（在 `release()` 里复位），
保证一次接管最多弹一条、状态行不被后者覆盖。

### 3.3 `readMs` 空串防御直接抄 `clampLimit` 的判空套路
`limits.ts:45-54` 已写好「空串/纯空白→NaN→回默认值」，`readMs`(:214) 复刻这几行即可，别重新发明：
```ts
const raw = getStoredValue<string>(SITE_ID, id);
const n = (typeof raw === 'string' && raw.trim() !== '') ? Number(raw.trim()) : Number.NaN;
if (!Number.isFinite(n) || n < 0) { log.warn(...); return fallbackMs; }
```
> 无法直接 `clampLimit(...)`：`clampLimit` 按 `LimitKey` 取预设 min/max/def，而 uooc 的毫秒项是独立的 fallback 语义；复用**套路**而非函数。

### 3.4 `aiConcurrency()` 的 1~8 钳位可更直白
`settings.ts:268-271` 用 `Math.min(8, Math.max(1, n))` 自造钳位。仓库已有 `clampLimit` 语义，但它是按 `LimitKey` 表取值的，**不建议**为单个 1~8 硬塞进 LIMITS（那会把"时间上限表"污染成杂物箱）。保持现状即可，或抽一个通用的 `clamp(n,min,max)` 纯函数放 `common/core/limits.ts`，供 `aiConcurrency` 与 `clampLimit` 复用——属于"可改可不改"。

### 3.5 顺带的小点
- `findByTc` 与 `byId`（tasks-model.ts:168/172）是同一件事的两种写法，只留 `byId`。
- `docs/` 下 23 份文档里旧连播/旧目录树的描述（C4）量很大，代码头注释（A4）先对齐是对的；文档正文清理可放到 C 组之后单独开分支。
