# 手测清单 —— 大纲与写作模板

> **本文档是什么**：手测清单（档 3）的**骨架与写法约定**，不是某一轮的具体清单。
> 写新一轮清单时**复制下面的骨架**，填进本轮内容，存成 `docs/手测清单-<主题>.md`。
> **本文档解决什么**：此前只有「格式」散落在三处（`docs/需求文档.md` §12 的四行格式、
> `docs/开发文档.md` §8.2 的表格与回话格式、`docs/交接文档.md`），**没有清单文件自身的骨架** ——
> 前置条件、范围与优先级、通过判据、回归范围、命名归档都无处可依，于是每轮靠临场发挥。

---

## 0. 命名与归档

| 项 | 约定 |
|---|---|
| 文件名 | `docs/手测清单-<主题>.md`。阶段/批次类用 `阶段2批1` 这种写法，修复类用主题名（如 `标签栏与悬浮球`） |
| 粒度 | **一轮一文件**（一次交付给用户的一批改动 = 一个文件），不要往旧文件里追加新一轮 |
| 抬头必写 | 被测产物路径 + **分支名** + **构建号**（产物头部「构建信息」行/启动日志里的 `v0.1.0#N`） |
| 与 §8.2 的关系 | `docs/开发文档.md` §8.2 是**总表**（历史累计条目），本轮清单是**本次要跑的子集**；跑完把结果回填 §8.2 |

> **执行方式**：装进 Tampermonkey → 逐条跑 → 逐条打勾
> **回话格式**：全过回「OK」；某条不过回「第 N 条：<现象>」+ Console 报错全文 + 截图
> **时间紧时**：先跑 <最关键的 2~4 条>

| 范围 | 条目 | 说明 |

- 全部条目达预期 ⇒ 回「OK」；

## 2. 写作铁律

1. **一条只测一个动作。** 「切标签页 + 刷新 + 换站点」是一条，因为它是**一个连续动作序列**；
   「看顺序对不对，顺便看看有没有报错」要拆成两条。
2. **「动作」必须是能照着做的物理操作。** 写「在 bkxk 页面点【本科选课设置】标签，然后按 F5」，
   不写「验证记忆功能」。不写鼠标坐标、不假设用户知道内部机制。
3. **「预期」必须可判定。** 写「仍停在【本科选课设置】」「球与关闭键**中心重合**（不偏移）」；
   不写「正常」「没问题」「应该工作」。
4. **预期里不要写实现细节。** 写用户看得见的结果（哪一页、哪个位置、有没有报错），
   不写「会调用 `resolveActiveTab`」。内部机制写进 `docs/开发文档.md`。
5. **风险条目单列并加标记。** 🔴 会留痕 / 可能封号的接口（抢课、退课）**必须单独分组**，
   标注「仅手动执行、不做自动化测试」，且**排在最后**跑。
6. **失败回传要具体到"贴什么"。** 每条指明三件套里要哪一件：
   Console 报错全文 / 该请求的 Request+Response / 截图（含哪些元素）。
7. **前置条件写清"从干净状态开始"还是"接着上一轮"。** 涉及存储的条目要写明
   「需要先清掉 `sztb:ui:active-tab:*`」这类前置动作，否则结果无法复现。
8. **不许把"档 1 能测的东西"塞进手测。** 纯函数（排序、键名、闸门）由 `npm test` 钉住，
   手测只覆盖**渲染 / 网络 / 存储 / 交互**这四类。

## 3. 反例对照

| ✗ 坏的写法 | ✓ 好的写法 |
|---|---|
| 动作「测试标签页记忆」 | 动作「切到【本科选课设置】后按 F5」 |
| 预期「正常记住」 | 预期「刷新后仍停在【本科选课设置】，且它高亮」 |
| 预期「球的位置应该对」 | 预期「球心与关闭键中心重合（截图里两处应在同一像素位置）」 |
| 失败贴回「有问题就告诉我」 | 失败贴回「Console 报错全文 + 收起/展开两张截图」 |
| 把抢课混在普通条目中间 | 抢课单独一节，标 🔴，注明「手动执行、可能留痕」，排最后 |

---

## 4. 回话格式（给用户的固定三档）

- **全过** ⇒ 回「OK」（一个字就够，不必复述条目）。
- **某条不过** ⇒ 「第 N 条：<现象原文>」+ Console 报错全文 + 该请求的 Request/Response + 截图（取适用的）。
- **多条不过** ⇒ 逐条列出，**不要合并成一句**「都失败了」—— 合并会丢掉区分线索。

> Console 报错请**整段复制**，不要只挑一行；本项目的启动期诊断是 `console.info`
> （`console.debug` 会被 Edge DevTools 默认过滤掉）。
